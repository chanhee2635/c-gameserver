# GameServer 부하 테스트 리포트 (동시접속 한계 측정)

작성일: 2026-06-07 (현재 빌드)
대상 빌드: 현재 작업 트리 Release x64 (`Binary/Release`, GameServer 06-07 빌드 — 시연 영상과 동일 빌드)

> 더미 클라이언트로 동시 접속자를 0 → 3,000명까지 단계적으로 올리며
> GameServer의 처리량/지연/무결성을 측정한다. **3,000명을 패킷 유실 0 · 평균 틱 지연 12ms로 안정 수용.**

---

## 1. 테스트 환경

| 항목 | 값 |
|---|---|
| CPU | Intel Core i5-1240P (12C / 16T, 노트북 P-시리즈) |
| RAM | 15.7 GB |
| OS | Windows 11 |
| 구성 | **단일 PC, localhost** — LoginWebServer(.NET8) + GateServer + GameServer + DummyClient 를 **한 머신에 동시 구동(co-located)** |
| 빌드 | Release x64, 현재 작업 트리 (시연 영상 녹화와 동일 빌드) |

**중요(정직성):** 서버 3종 + 부하 생성기가 같은 PC에서 16스레드를 나눠 쓴다.
따라서 아래 CPU%는 **GameServer 프로세스 단독 점유율**이며, 머신 전체는 그보다 더 바빴다.
즉 이 수치는 "전용 서버 머신의 한계"가 아니라 **개발 PC 1대에서 서버와 부하기를 동시에 돌렸을 때의 보수적 하한선**이다.

### 서버 설정 (`server.json`)

- `maxSessions` 3000, `acceptPool` 256
- `world`: mapSize 1000×1000, zoneSize 20 → **2,500 Zone**, **sceneCount 8**
- `gameplay.updateTickMs` 50 → scene당 목표 20틱/s, 8 scene = **목표 160틱/s**
- `HEARTBEAT_MS` 500, 이동 변화는 임계치(`ShouldBroadcastMove`)로 즉시 송신
- DB(MySQL) / Redis 연동 활성, **몬스터 스폰은 부하 테스트에서 비활성**(순수 플레이어 브로드캐스트 부하 측정)

### 부하 시나리오 (더미 행동)

- 각 더미: **100ms마다 `C_MOVE` 1개** 전송 → 더미당 10패킷/s (3000명 = 이론상 30,000 move/s)
- 부하 생성기(DummyClient)는 **16그룹(액터)×8워커**로 병렬 생성 (id 라운드로빈 분배)
- 1000×1000 맵에 균일 랜덤 분포로 직선 배회
- 램프: `500 → 1000 → 1500 → 2000 → 2500 → 3000`, 각 단계 25초 유지(정상상태 확보)

### 측정 방법

- GameServer의 `ServerStats` 상태 패널(1초 주기)을 파일로 캡처(`game_run.log`)
- 파서(`/.loadtest/parse.awk`)로 프레임당 1행 CSV로 변환 후 동접 구간별 집계
- 카운터: In/Out pkt/s(논리 패킷·Send 단위), IOCP/s, Job/s, AvgLag/MaxLag(틱 스케줄 대비 지연)

## 3. 핵심 결론

1. **단일 PC에서 3,000 동시 접속을 패킷 유실 0으로 안정 수용.** 전 구간에서
   `droppedPackets = 0`, `recvBacklog = 0`, `dbFailed = 0`.
2. **CPU는 동접에 거의 선형, 3,000에서도 ~22%.** 500→0.7%, 2000→11%, 3000→~22%. 메모리 50→73MB로 평탄.
3. **틱 지연이 평탄하다.** AvgLag는 전 구간 12ms, 3,000 정상상태 MaxLag ~13ms. 직전 빌드에서 2,000명 한 틱
   최대 1.6초까지 밀던 현상(6장)을 **send-lane 병렬화 + 하트비트 500ms + 이동 변화 게이팅**으로 제거.
4. **송신 파이프라인이 버텼다.** ~4.9 MB/s 송신·합산 80k pkt/s에서도 백로그 0.

## 4. 발견 사항 / 한계

### ① 측정 환경의 보수성 (프로세스 CPU vs 머신 전체)
- 표의 CPU%는 GameServer 프로세스 단독값이다. 같은 PC에서 Login/Gate/더미가 코어를 함께 쓰므로
  머신 전체 CPU는 그보다 높았다. **전용 머신이라면 더 높은 동접이 가능**하다.

### ② 부하 테스트는 순수 플레이어 브로드캐스트 부하
- 몬스터 스폰을 끈 상태(Monsters: 0)로 IOCP 수신 + AOI 브로드캐스트 경로를 한계까지 미는 데 집중했다.

### ③ Suspicious(이동 검증 거부) — ~2,500명부터 소량 발생
- ~2,500명 구간부터 `Suspicious` 카운터가 간헐적으로 조금씩 증가하기 시작했다. 같은 구간에도 Drop/Backlog/DB 실패는 0.
- **원인 분석(코드 근거):** 더미는 100ms마다 고정 거리 스텝(`MOVE_SPEED × 0.1s`)으로 이동을 보고하고,
  서버 속도 게이트([`Player::IsMoveAllowed`](../GameServer/Player.cpp))는 「마지막 승인 이후 경과시간 dt × 최대속도 × 1.5(지터 허용), dt는 1s로 캡」을
  넘는 이동을 거부한다. 단일 PC 과구독(서버 8워커 + 더미 8워커 + Login/Gate가 16스레드 경쟁) 구간에서 더미 송신·서버 틱
  타이밍이 흔들리면, **관측 dt가 더미의 송신 간격보다 짧게 측정되는 순간 고정 100ms분 스텝이 허용 거리를 초과** →
  거부 + `S_MOVE_CORRECTION` 롤백 + Suspicious 집계. 더미가 보정을 수용해 즉시 복귀하므로 수치가 폭증하지 않고 소량씩 쌓인다.
- **해석:** 치팅이 아니라 **공유 머신의 타이밍 왜곡이 검증 게이트에 걸린 것**. 역으로 풀 부하에서도 검증→거부→롤백
  경로가 동작하고 시뮬레이션이 깨지지 않음을 보여준다(좌표 드리프트·유실 0 유지). 서버는 '지연된 정상 클라'와
  '순간이동'을 구분할 수 없으므로, 즉시 차단 대신 **롤백 보정**으로 대응하는 현재 설계가 부하에서도 유효했다.
- **검증 예정:** 부하기를 별도 머신으로 분리하면(5장 1번) Suspicious ≈ 0 예상 — 분리 측정 시 함께 확인.

### ④ 베이스라인 틱 ~128/s (목표 160/s)
- 부하 무관하게 틱레이트 ~128/s, AvgLag ~12ms 상수 — `JobTimer→IocpDispatch→Distribute→Update`
  스케줄링 파이프라인 지연으로 추정(2026-05-30 [`tick-performance-analysis.md`](./tick-performance-analysis.md) 진단과 일치).

### ⑤ 종료 시 DummyClient segfault (런타임 무관)
- 램프 완주 후 `q` 종료하는 셧다운 경로에서 segfault — 측정엔 영향 없으나 cleanup 순서 버그, 별도 수정 권장.

## 5. 다음 단계 (스케일업 로드맵)

1. **다중 머신 부하** — 더미를 별도 머신에서 돌려 서버 단독 한계(3,000 이상) 측정.
   (단일 PC에선 서버 8워커 + 더미 8워커가 16코어를 다퉈 더미가 천장.)
2. **전용 머신 측정** — 서버와 부하기 분리로 "서버 단독" CPU/한계 재측정.
3. **AOI 인원 제한·Hysteresis 마진** — 핫스팟(한 존 밀집) 트래픽 상한 도입.
   (참고: [`AOI_MOVEMENT_PIPELINE.md`](../AOI_MOVEMENT_PIPELINE.md))
4. **장시간 소크 테스트** — 수 시간 유지하며 메모리 평탄선 확인(누수 검증).
5. 셧다운 segfault 수정, 틱 베이스라인 ~128/s 파이프라인 단축 검토.

## 6. Before / After (직전 빌드 대비 개선)

| 지표 | Before (05-30, sceneCount=4, 단일 Job 송신) | After (06-07, sceneCount=8, send-lane + HB 500ms) |
|---|---|---|
| 측정 동접 | 2,000명 | **3,000명** |
| 평균 틱 지연(AvgLag) | 44 ~ 110 ms | **12 ms** |
| 최악 틱 지연(MaxLag) | 356 ~ **1,606 ms** | 정상 ~13ms (스폰 버스트 순간 ≤60ms) |
| Scene 틱레이트 | 28 ~ 46 /s | **128 /s** |
| 프로세스 CPU | 17 ~ 21 % (2,000명) | ~22 % (3,000명) |
| 패킷 유실 | 0 | 0 |

> 핵심: 직전 빌드가 **2,000명에서** 한 틱 최대 1.6초까지 밀리던 것을, 현재 빌드는 **3,000명에서도**
> 평균 12ms로 평탄화. "단일 Job 브로드캐스트가 워커 1개를 독점"하던 구조 병목을 zone별 send-lane 풀로
> 병렬화해 해결했다. (분석: [`tick-performance-analysis.md`](./tick-performance-analysis.md), [`troubleshooting.md`](./troubleshooting.md))

### 재현 방법

```bash
# Release 재빌드 후 (Redis/MySQL 구동 상태에서)
bash .loadtest/rampfull.sh                     # 램프 실행, game_run.log 캡처
tr -d '\000' < .loadtest/game_run.log \
  | sed 's/\x1b\[[0-9;]*[A-Za-z]//g' | tr '\r' '\n' \
  | gawk -f .loadtest/parse.awk > .loadtest/timeline_run.csv
```
