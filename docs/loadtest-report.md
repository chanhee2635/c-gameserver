# GameServer 부하 테스트 리포트 (동시접속 한계 측정)

작성일: 2026-06-02
대상 빌드: `feature/tick-phase-metrics` 작업본 (현재 코드 그대로 Release 재빌드)

> 더미 클라이언트로 동시 접속자를 0 → ~3,000명까지 단계적으로 올리며
> GameServer의 처리량/지연/무결성을 측정하고 한계 지점을 찾는다.

---

## 1. 테스트 환경

| 항목 | 값 |
|---|---|
| CPU | Intel Core i5-1240P (12C / 16T, 노트북 P-시리즈) |
| RAM | 15.7 GB |
| OS | Windows 11 |
| 구성 | **단일 PC, localhost** — LoginWebServer(.NET8) + GateServer + GameServer + DummyClient 를 **한 머신에 동시 구동(co-located)** |
| 빌드 | Release x64, 현재 작업 트리 그대로 재빌드 |

**중요(정직성):** 서버 3종 + 부하 생성기가 같은 PC에서 16스레드를 나눠 쓴다.
따라서 아래 CPU%는 GameServer 프로세스 단독 점유율이며, 머신 전체는 그보다 훨씬 더 바빴다.
즉 이 수치는 "전용 서버 머신의 한계"가 아니라 **개발 PC 1대에서 서버와 부하기를 동시에 돌렸을 때의 보수적 하한선**이다.

### 서버 설정 (`server.json`)

- `maxSessions` 3000, `acceptPool` 256
- `world`: mapSize 1000×1000, zoneSize 20, **sceneCount 8**
- `gameplay.updateTickMs` 50 → scene당 목표 20틱/s, 8 scene = **목표 160틱/s**
- DB(MySQL) / Redis 연동 활성

### 부하 시나리오 (더미 행동)

- 각 더미: **100ms마다 `C_MOVE` 1개** 전송 → 더미당 10패킷/s (3000명 = 이론상 30,000 move/s)
- 1000×1000 맵에 균일 랜덤 분포로 직선 배회, 도착 시 새 목표 선택
- 채팅은 50~100초에 1회(무시 가능 수준), 1% 확률로 월드챗
- 램프: `500 → 1000 → 1500 → 2000 → 2500 → 3000`, 각 단계 **25초 유지**(정상상태 확보) 후 상위 25초 홀드

### 측정 방법

- GameServer의 `ServerStats` 상태 패널(1초 주기)을 파일로 캡처
- 파서(`/.loadtest/parse.awk`)로 프레임당 1행 CSV(`timeline_run.csv`)로 변환 후 동접 구간별 집계
- 드라이버/파서: `/.loadtest/rampfull.sh`, `/.loadtest/parse.awk`

카운터 의미(코드 확인):
- **In pkt/s** = `recvPackets` — `OnRecv`에서 **논리 패킷 1개당 +1** (진짜 수신 패킷률)
- **Out pkt/s** = `sendPackets` — `Send` 호출(WSASend 등록) 단위
- **IOCP/s** = IOCP 완료 디스패치 횟수, **Job/s** = JobQueue 실행 잡 수
- **AvgLag/MaxLag** = 틱이 예정 스케줄(50ms) 대비 밀린 시간

## 3. 핵심 결론

1. **단일 PC에서 ~2,950 동시 접속을 패킷 유실 0으로 수용.** 전 구간에서
   `droppedPackets = 0`, `recvBacklog = 0`, `dbFailed = 0` — 수신/송신/DB 어디서도 밀리거나 흘리지 않았다.
2. **아웃바운드(브로드캐스트) 처리량이 실질 부하의 주축.** 3,000명 구간에서
   `S_UPDATE_SCENE`를 초당 ~27,000개(피크 39,586), **28.8 MB/s**까지 안정적으로 토해냈다.
3. **CPU는 동접에 거의 선형.** 500→3.2%, 1500→19.8%, 3000→53%. 메모리는 부하 중 0.49→0.70 GB로
   완만히 증가 후 평탄 — 폭주/누수 징후 없음.
4. **송신 파이프라인이 버텼다.** Send 큐 최대 깊이 45(임계 128의 35%)로, 프레임별 모아쏘기 +
   send-lane 분산 구조가 28 MB/s 송신에서도 적체되지 않았다.

## 4. 발견 사항 / 한계

### ① 서버 측 포화 시작점 ≈ 2,500명 (브로드캐스트 바운드)
- 틱레이트가 목표 160/s 대비 ~128/s(저부하)에서 2,500명부터 116~117/s로 하락,
  AvgLag 12 → 17~19ms 상승. 한 scene 틱 안의 **`BroadcastScene`(PosInfo 직렬화 + 송신)** 비중이
  커지며 50ms 예산을 압박. 인바운드가 아니라 **송신/브로드캐스트가 한계 요인**이다.
- → AOI(관심영역) 송신량 축소가 다음 스케일업의 핵심. (참고: [`AOI_MOVEMENT_PIPELINE.md`](../AOI_MOVEMENT_PIPELINE.md))

### ② 상수 베이스라인 틱 지연 ~12ms
- 부하와 무관하게 idle에도 AvgLag ~12ms, 틱레이트 160 대신 ~128/s. 컴퓨팅 비용이 아니라
  `JobTimer → IocpDispatch(timeout) → Distribute → Update` **스케줄링 파이프라인 지연**으로 추정.
  영향 경미하나 틱레이트 상한을 깎는 요인. (2026-05-30 [`tick-performance-analysis.md`](./tick-performance-analysis.md) 진단과 일치)

### ③ 부하 생성기(DummyClient)가 ~2,000명부터 병목
- 2,000명 이후 **In pkt/s가 오히려 감소**(14k→7~9k). 서버 drop/backlog가 0이므로 서버가 흘린 게 아니라
  **더미가 충분히 못 쏜 것.** DummyClient는 단일 시뮬레이션 스레드가 매 루프 전체 에이전트를 락 잡고 순회하므로,
  같은 PC에서 서버와 CPU를 다투면 3,000 에이전트 분 10Hz 생성을 못 채운다.
- → 즉 **인바운드 실측 상한(~22k/s)은 서버 한계가 아니라 측정 도구 한계**다. 더 정확한 수신 한계 측정에는
  멀티 스레드 더미 또는 **여러 머신에서 부하 분산**이 필요.

### ④ 종료 시 DummyClient segfault (런타임 무관)
- 램프 정상 완주(RAMP-END 도달) 후 `q` 입력으로 종료하는 **셧다운 경로에서 segfault**.
  테스트 데이터에는 영향 없으나 정리(cleanup) 순서 버그로 보임 — 별도 수정 권장.

### ⑤ 빌드 차단 수정 (테스트 진행을 위해 적용)
- 현재 작업 트리는 DummyClient 링크 실패 상태였다: proto에 `S_MOVE_CORRECTION`이 추가되고
  핸들러가 등록/선언됐으나 **DummyClient 측 구현이 누락**(`OnHandle_S_MOVE_CORRECTION` LNK2001).
  부하 더미는 보정 패킷을 적용할 필요가 없어 **no-op 핸들러**를 추가해 빌드를 통과시켰다
  (`DummyClient/ServerPacketHandler.cpp`).

## 5. 다음 단계 (스케일업 로드맵)

1. **AOI 송신량 축소** — 동일 zone 격자 단위 직렬화 공유/우선순위 대역폭 제어로 Out pkt/s 절감 → 2,500명 천장 돌파.
2. **분산 부하 생성** — 멀티 스레드 더미 또는 다중 머신으로 인바운드 실한계(서버 recv 한계) 별도 측정.
3. **전용 머신 측정** — 서버와 부하기를 분리해 "서버 단독" CPU/한계 재측정(현 수치는 보수적 하한).
4. **장시간 소크 테스트** — 1~2k 동접을 수 시간 유지하며 메모리 평탄선 확인(누수 검증). (이번 런은 단시간이라 누수 판단 불가)
5. 셧다운 segfault 수정, 틱 베이스라인 12ms 파이프라인 단축 검토.

## 6. 포트폴리오용 한 줄 요약 (정직 버전)

> 개발 PC 1대(i5-1240P, 16T)에 인증 웹서버·게이트·게임서버·부하기를 모두 올린 환경에서
> 더미 클라이언트로 **~2,950 동시 접속**까지 램프업, **패킷 유실 0 / 수신 백로그 0 / DB 실패 0**으로 수용.
> 피크 합산 처리량 **약 55,000 패킷/s(아웃 28.8 MB/s)**, 게임서버 CPU 53% / 메모리 0.7 GB.
> 한계 요인을 **브로드캐스트(아웃바운드) 바운드(≈2,500명부터 틱 예산 압박)**로 데이터로 특정했고,
> 인바운드는 동일 PC의 **부하 생성기 한계**여서 서버 수신 한계와 구분해 기록함.

### 재현 방법

```bash
# Release 재빌드 후
bash .loadtest/rampfull.sh                     # 램프 실행, game_run.log 캡처
tr -d '\000' < .loadtest/game_run.log \
  | sed 's/\x1b\[[0-9;]*[A-Za-z]//g' | tr '\r' '\n' \
  | gawk -f .loadtest/parse.awk > .loadtest/timeline_run.csv
```
